 TEAM APP — getting it running
 Follow in order. Steps 1-5 are yours (I'm not allowed to create accounts
 or type passwords for you). Everything after step 6 is mine.
══════════════════════════════════════════════════════════════════════

 USE YOUR EXISTING SUPABASE LOGIN. MAKE A NEW *PROJECT*.

 Same rule as always: one account, separate projects. A new project means
 a brand new database that cannot touch AeroPark's or Sahasra's data.


──────────────────────────────────────────────────────────────────────
 STEP 1 — create the project
──────────────────────────────────────────────────────────────────────
 supabase.com/dashboard → New project

   Name:      team-app
   Password:  "Generate a password", then SAVE IT somewhere safe
   Region:    London (eu-west-2)   <- your clients are UK
   Plan:      Free

 *** NEVER send that database password to me or anyone else. ***


──────────────────────────────────────────────────────────────────────
 STEP 2 — build the tables
──────────────────────────────────────────────────────────────────────
 SQL Editor → New query.
 Open setup/schema.sql, select ALL, copy, paste, Run.

 Expect "Success. No rows returned". That's correct.


──────────────────────────────────────────────────────────────────────
 STEP 3 — create your first company
──────────────────────────────────────────────────────────────────────
 SQL Editor → New query. Change the name, then Run:

   insert into companies (name) values ('247 Airport Parking')
   returning id;

 COPY THE ID IT PRINTS BACK. You need it in step 5.

 Later, each new client you sell to = one more row here. Same app,
 same database, walled off from each other.


──────────────────────────────────────────────────────────────────────
 STEP 4 — create your own login
──────────────────────────────────────────────────────────────────────
 Authentication → Users → Add user → Create new user

   Email:    your email
   Password: a strong one, save it in a password manager
   Tick:     "Auto Confirm User"


──────────────────────────────────────────────────────────────────────
 STEP 5 — make yourself the owner
──────────────────────────────────────────────────────────────────────
 SQL Editor → New query. Put YOUR email and the company id from step 3:

   insert into profiles (id, company_id, full_name, role)
   select u.id, 'PASTE-COMPANY-ID-HERE', 'Rakesh', 'owner'
   from auth.users u where u.email = 'your@email.com';

 Should say "Success. 1 row". If it says 0 rows, the email doesn't match
 what you typed in step 4 — check the spelling.

 ⚠️ Creating a login is NOT enough on its own, on purpose. A person can
 only get in once they have a row in `profiles`. That's what stops a
 stranger who signs up from seeing any client's data.


──────────────────────────────────────────────────────────────────────
 STEP 5b — TURN OFF PUBLIC SIGN-UPS
──────────────────────────────────────────────────────────────────────
 Authentication → Sign In / Providers → Email
 Switch OFF "Allow new users to sign up". Save.

 Without this, strangers can create themselves an account. They still
 couldn't see anything (step 5 is what grants that) — but there's no
 reason to let them in at all.

──────────────────────────────────────────────────────────────────────
 THEN — adding a client, and adding their staff
──────────────────────────────────────────────────────────────────────
 New client company:
   insert into companies (name) values ('A-Z Auto Spares') returning id;

 Their manager / each staff member:
   1. Authentication → Users → Add user (email + password, Auto Confirm)
   2. SQL Editor:
        insert into profiles (id, company_id, full_name, role)
        select u.id, 'THEIR-COMPANY-ID', 'Their Name', 'staff'
        from auth.users u where u.email = 'them@example.com';

      role is 'staff', 'admin' or 'owner'.
      staff  = clock in/out, see only their own shifts
      admin  = the whole board, timesheets, staff, sites
      owner  = same as admin (kept separate so you can restrict later)

 Worksites are added from the admin screen — stand in the yard and press
 "Use my location", which saves hunting for coordinates.


──────────────────────────────────────────────────────────────────────
 WHAT EACH FILE IS
──────────────────────────────────────────────────────────────────────
 index.html  — the staff app. Clock in/out, see your own shifts.
                This is the one that becomes the phone app.
 admin.html  — the manager board. Who's on now, timesheets, CSV export,
                staff, worksites.

 Both need the two lines from step 6 pasting into the settings block at
 the top of the file.


──────────────────────────────────────────────────────────────────────
 ABOUT THE LOCATION CHECK — say this plainly to clients
──────────────────────────────────────────────────────────────────────
 It records where someone was AT THE MOMENT they clocked in and out.
 It does NOT track anyone in between, and the app stores no location
 outside those two moments.

 It stops someone clocking in from bed. It does NOT stop a determined
 faker with a spoofing app on a rooted phone. Sell it as an honesty
 check, not surveillance — overselling it is how you get an argument
 with a staff member you can't win.

 If someone's GPS fails or they refuse permission, the shift still
 records — flagged as unverified for a manager to look at. A refused
 clock-in would mean an unpaid shift, which is a far worse failure.


 ATTENDANCE UPGRADE: CORRECTIONS AND HOME-SCREEN INSTALLATION
 ---------------------------------------------------------
 For an existing company database, run the updated setup/schema.sql:
 1. In Supabase, open this project's SQL Editor and click New query.
 2. Put the full contents of setup/schema.sql into the editor.
 3. Click Run and check that it succeeds before publishing the new app.
    The update runs in a transaction and is safe to rerun with existing data.
 4. Test a correction with a staff account. Sign in as a different manager,
    open Review, and approve or reject it. Check the timesheet afterwards.

 Requests retain the original times, reason and manager decision. Staff
 cannot approve their own corrections. Approvals reject overlapping times
 and requests whose original shift has changed since submission.

 Local HTML previews always use disposable sample data. Each demo page
 has its own in-memory data; a refresh resets it. The manager Review tab
 includes a sample request. The live database is never used by local files.

 Hosted HTTPS is needed for home-screen installation. On iPhone/iPad use
 Safari > Share > Add to Home Screen. Android and desktop browsers can
 offer Install Aero from Account, or installation through the browser menu.
 Attendance is not cached or queued offline: reconnect to record a shift.

 Alerts are in-app while the page is open, not email, SMS or background
 push. The manager board refreshes requests every 30 seconds. Staff see
 approval decisions in Activity. Long-shift reminders appear after 13 hours.

 Exports stay in one combined CSV. Completed shifts are selected by default;
 clear that checkbox to include running shifts. Print / PDF opens the
 browser's print dialogue, where Save as PDF is available on supported devices.
